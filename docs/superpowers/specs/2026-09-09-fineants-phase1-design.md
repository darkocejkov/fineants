# fineants — Phase 1 design: SimpleFin sync, storage, and basic dashboards

**Date:** 2026-09-09
**Status:** Approved

## 1. Purpose

fineants is a personal finance dashboard. It pulls real banking data from a SimpleFin
Bridge account, accumulates it locally, and shows it in dashboards. Later phases add
manually entered data (external debts, recurring costs, budgets) and a JSON feed for a
Magic Frame display.

Phase 1 delivers:

- A reliable, rate-limit-respecting sync from SimpleFin into a local SQLite database.
- A raw data explorer so the owner can see exactly what SimpleFin exposes for their banks.
- Basic dashboards: account balances, net worth over time, transactions, spending.
- A minimal read-only JSON API protected by an API key, ready for Magic Frame in phase 3.

Out of scope for phase 1 (designed for, not built): external debts, recurring costs and
budgeting, transfer detection between own accounts, transaction categorisation, the Magic
Frame module itself, authentication for the dashboard UI.

## 2. Decisions already made

| Decision | Choice | Why |
| --- | --- | --- |
| Language | TypeScript throughout | Magic Frame is JS; one language for both |
| Framework | Next.js (App Router), latest stable | Owner's preference |
| Storage | SQLite file via Drizzle ORM + better-sqlite3 | Single-user, zero setup, one file to back up |
| Runtime | Docker on an always-on home server | Enables scheduled sync and Magic Frame polling |
| Structure | Single Next.js container, library-first | Least infra; logic in `src/lib` reusable from CLI, routes, scheduler |
| Magic Frame integration | Magic Frame pulls JSON from fineants | Stateless, simple |
| Phase 1 boundary | Bank data only | See something working before adding manual data |

## 3. SimpleFin facts the design depends on

Verified against simplefin.org/protocol.html and beta-bridge.simplefin.org/info/developers
on 2026-09-09.

- A **setup token** is a base64-encoded claim URL. `POST` to it once (empty body) returns an
  **access URL** of the form `https://user:pass@host/simplefin`. The setup token is
  single-use; a second claim returns 403.
- Data is fetched with `GET {accessUrl}/accounts` and query params `start-date`,
  `end-date` (Unix seconds; end is exclusive), `pending=1`, `account=<id>` (repeatable),
  `balances-only=1`.
- The date range of a single request is limited to **90 days**. The bridge recommends
  overlapping consecutive windows by about **5 days**.
- The bridge targets daily updates from banks and expects **24 requests or fewer per day**,
  ideally at a random minute offset (e.g. every 6 hours at :17).
- Amounts and balances are **numeric strings**; dates are **Unix seconds** (integers).
  Positive amount = deposit.
- Two response shapes exist in the wild and the parser must accept both:
  - Older bridge shape: `{ errors: string[], accounts: [{ org: {domain, name, sfin-url, url, id}, id, name, currency, balance, "available-balance", "balance-date", transactions: [{ id, posted, amount, description, payee, memo, transaction_id, pending }], holdings, extra }] }`
  - Newer protocol shape: `{ errlist: [{code, msg, conn_id?, account_id?}], connections: [{conn_id, name, org_id, org_url?, sfin_url}], accounts: [{ id, name, conn_id, currency, balance, "available-balance", "balance-date", transactions: [{ id, posted, amount, description, transacted_at?, pending?, extra? }], extra? }] }`
- HTTP 403 = credentials revoked or invalid; 402 = payment required at the bridge.
- A demo setup token is published on the developers page for testing without real data.

## 4. Architecture

```
docker compose
 └─ fineants (Next.js standalone, Node runtime)
     ├─ instrumentation.ts  → startScheduler() → lib/sync
     ├─ app/(pages)         → lib/queries (server components read SQLite directly)
     ├─ app/api/sync        → lib/sync      (POST, x-api-key or same-origin)
     ├─ app/api/v1/*        → lib/queries   (GET, x-api-key; for Magic Frame)
     └─ scripts/claim.ts, scripts/sync.ts → lib/*
 volume: ./data → /data  (fineants.db)
```

Layering rule: everything under `src/lib` is plain TypeScript with **no imports from
`next/*` or React**. Routes, pages, scripts, and the scheduler are thin adapters over it.

fineants.

## 6. SimpleFin client

`fetchAccounts(accessUrl, { start, end, pending = true, accountIds? })`:

1. Builds the URL, sends `GET` with `Accept: application/json`. Credentials come from the
   access URL's userinfo; the client sends them as an `Authorization: Basic` header rather
   than relying on fetch to honour userinfo.
2. Maps status codes: 200 → parse; 403 → `SimpleFinAuthError`; 402 → `SimpleFinPaymentError`;
   other non-2xx → `SimpleFinHttpError(status, bodySnippet)`. Network failures →
   `SimpleFinNetworkError`.
3. Parses with a zod union of the two shapes using `.passthrough()` so unknown fields
   survive into `raw`. Normalises into `{ connections: Connection[], accounts: Account[],
   errlist: ErrItem[] }` where old-shape string errors become `{ code: "gen.legacy", msg }`.
4. Returns `{ normalised, rawBody, httpStatus }`.

`claimSetupToken(token)` base64-decodes, `POST`s with `Content-Length: 0`, and returns the
access URL text. Used only by `scripts/claim.ts`; the server never claims automatically
because the token is single-use and the owner must see and store the result.

## 7. Sync engine

`runSync({ trigger, force = false, now = Date.now() })`:

1. **Preconditions.** If `credentials_invalid` is set and not `force`, return a skipped
   summary. If the last run started under 30 minutes ago and not `force`, return skipped
   (rate guard).
2. **Windows.** `computeWindows(lastSuccessEnd, now, backfillDays)`:
   - No previous success → backfill: windows of ≤90 days from `now - backfillDays` up to
     `now`, each overlapping the previous by 5 days, oldest first.
   - Previous success → single window `[lastSuccessEnd - 5 days, now]`, split into ≤90-day
     chunks if the gap is large (e.g. the server was off for months).
3. **Per window**, inside one SQLite transaction:
   - Insert a `sync_runs` row with status `running`.
   - Fetch. On `SimpleFinAuthError`, set `credentials_invalid`, mark the run `failed`, stop.
   - Upsert connections and accounts (`last_seen_at = now`; user-set columns untouched).
   - Upsert transactions on `id`. Update `pending`, `posted`, `amount_cents`, etc. from the
     wire so a pending row that later posts under the same id is corrected in place.
   - **Pending reconciliation.** Delete rows where `pending = 1`, `account_id` is among the
     accounts returned, and `transacted_at`/`posted`/`first_seen_at` falls inside the window,
     but whose `id` was not in the response.
   - Insert one `balance_snapshots` row per account.
   - Update `last_successful_sync_end = window.end` and mark the run `success`, or `partial`
     if `errlist` is non-empty.
4. Return a summary `{ runs: SyncRunSummary[], skipped?: reason }`.

Errors from SimpleFin's `errlist` never fail the run; they are stored and surfaced in the UI.

## 8. Scheduler

`instrumentation.ts` → `register()` → if `process.env.NEXT_RUNTIME === "nodejs"` and
`SYNC_INTERVAL_HOURS > 0`, call `startScheduler(config)`:

- Guard with `globalThis.__fineantsScheduler` so dev hot reloads do not start a second timer.
- On start, if `last_successful_sync_end` is older than the interval, run once immediately
  (`trigger: "scheduled"`).
- Pick or reuse `scheduler_minute_offset` (random 0–59, persisted in `app_state`), then
  schedule the next run at the next `interval` boundary plus that offset, and repeat.
- Wrap each run in try/catch and log; a failure never kills the timer.

`.env.example` committed; `.env` gitignored.

| variable | required | default | purpose |
| --- | --- | --- | --- |
| SIMPLEFIN_ACCESS_URL | for sync | — | `https://user:pass@…/simplefin` from the claim step |
| SIMPLEFIN_SETUP_TOKEN | no | — | read only by `npm run claim` |

| SYNC_INTERVAL_HOURS | no | `6` | `0` disables the scheduler |
| BACKFILL_DAYS | no | `365` | first-sync history depth |
| API_KEY | for API | — | required by `/api/sync` and `/api/v1/*` via `x-api-key` |
| PORT | no | `3000` | |

Config is parsed once with zod in `lib/config.ts`; a missing required value fails fast
with a clear message at the point of use (sync or API), not at boot, so the UI still
loads for the explorer and settings before credentials exist.

Dashboard pages have **no authentication**; the deployment assumption is LAN-only access.

## 10. UI

Server components query SQLite through `lib/queries`. Client components are limited to
charts (Recharts), the Sync now button, and form controls. Tailwind for styling; small,
consistent, dark-mode-aware.

| route | content |
| --- | --- |
| `/` Overview | totals by currency (non-hidden accounts), account cards (nickname or name, type, balance, balance date), net-worth sparkline from snapshots, last sync status + Sync now, recent 20 transactions, error banner when latest run has errlist or `credentials_invalid` |
| `/transactions` | paginated table (50/page): date, account, description/payee, amount, pending badge; filters: text search, date range, account; sort by posted desc |
| `/accounts/[id]` | header with balances, balance-history line chart from snapshots, that account's transactions with the same filters |
| `/spending` | range selector (7d, 30d, 90d, 12m); outflow bars by day/week/month; inflow vs outflow totals; top 10 payees/descriptions by outflow. Hidden accounts excluded. No transfer detection yet, stated in the page footer |
| `/explorer` | sync runs table (time, trigger, status, window, counts, errors); `/explorer/[runId]` shows the normalised errlist and the raw response pretty-printed in collapsible sections per account |
| `/settings` | per-account nickname, type, hidden (server actions); shows scheduler status and configured interval |

Empty states: every page renders a helpful message when there has been no successful sync,
linking to the explorer/settings and describing the claim step.

## 11. API

All routes under `/api` require header `x-api-key: <API_KEY>`; `POST /api/sync` also accepts
same-origin requests from the Sync now button (checked via `Origin`/`Sec-Fetch-Site`).

- `POST /api/sync?force=1` → `runSync({ trigger: "manual", force })` → 200 with summary, or
  409 when skipped by the rate guard, 503 when credentials are invalid.
- `GET /api/v1/summary` → `{ generatedAt, lastSync: {finishedAt, status}, totals: [{currency, balanceCents}], accounts: [{id, name, type, currency, balanceCents, balanceDate}] }` (non-hidden only).
- `GET /api/v1/spending?range=today|7d|30d` → `{ range, currency, days: [{date, outflowCents, inflowCents}], topPayees: [...] }`.

Responses are JSON with cents as integers; formatting is the consumer's job.

## 12. Testing

Vitest. Tests do not hit the network.

- **Unit**: `money.ts` (parsing "-12.34", "1000", "0.5", negative zero, >2 decimals →
  error), `windows.ts` (no history, recent history, long gap, boundary at exactly 90 days,
  overlap), `simplefin/schema.ts` (fixtures for old shape, new shape, errlist-only, empty
  accounts, unknown extra fields preserved).
- **Integration** (in-memory SQLite, mocked `fetch`): first backfill issues N requests and
  stores snapshots; incremental sync upserts and updates a pending → posted transaction;
  pending reconciliation deletes vanished pending rows; errlist yields `partial`; 403 sets
  `credentials_invalid` and the next run is skipped; rate guard skips within 30 minutes.
- **API**: route handlers reject missing/wrong key, return the documented shapes.

## 14. Error handling summary

| situation | behaviour |
| --- | --- |
| SimpleFin errlist entries | stored on the run, run marked `partial`, banner on overview |
| HTTP 403 | `credentials_invalid` set; scheduler skips until `SIMPLEFIN_ACCESS_URL` changes (its hash is stored alongside the flag) |
| HTTP 402 / other | run `failed` with message; retried next interval |
| network failure | run `failed`; retried next interval |
| parse failure | run `failed`, raw body still stored for the explorer |
| rate guard | run skipped; UI shows "synced N minutes ago" |

## 15. Phase roadmap

1. **Phase 1 (this spec)**: sync, storage, explorer, dashboards, minimal API.
2. **Phase 2**: external debts and payments, recurring costs and simple budgets, transaction
   metadata (category, transfer flag), Settings pages for all of it.
3. **Phase 3**: Magic Frame module polling `/api/v1/*`; richer daily summary endpoint;
   reminders for upcoming recurring costs and debt due dates.
